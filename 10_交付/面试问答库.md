# 面试问答库 · dw-etl-pipeline

> 12 题，按「选型 3 / 最难 3 / 再做一次 2 / 细节深挖 4」配比。案例均来自 `_失败日志.md` 与 `_问题台账.md`；数字只取实测产物。

## ① 选型对比

### Q1. 为什么用 MySQL 存储过程做 ETL，不用 Airflow + Python 调度？

- 30 秒版：本项目是单机日批、单库、90 天数据，16GB 内存，目标是把四层链路和幂等做扎实，不是搭调度平台。存储过程把 ODS→DWD→DWS→ADS 放在数据库内执行，少一层跨进程传输；Airflow 的调度、重试、可视化对单人项目是额外运维成本。
- 追问 1：存储过程难维护怎么办？→ 5 个过程按层拆分，参数只有日期，`etl_run_log` 记录每层行数，失败按层续跑；复杂逻辑（DQ 规则、对账）放 Python，SQL 只做集合运算。
- 追问 2：跨库/大数据量怎么办？→ 这个方案的前提是单库、百万级以内；再大就要把重算交给 Spark，存储过程只保留调度与轻量聚合。
- 追问 3：调度失败怎么发现？→ `run_daily` 退出码 0/2/3/4/5 + `run_summary.json`，外层 cron 或 CI 读退出码即可告警。
- 答不上来时：Airflow 我只做过原理对照，没有生产调度经验；这个项目刻意把调度压到脚本层，是为了先保证链路正确。

### Q2. 为什么 Spark 和 pandas 双引擎，不只用 Spark？

- 30 秒版：本机是 Windows + 16GB 内存，Spark `local[2]` 能跑通 90 天重算，但偶发 worker 回连失败。pandas 同口径实现是兜底，也是对账的独立第二实现；报告必须写真实引擎，不能 Spark 失败还写 Spark。
- 追问 1：两套实现口径怎么保证一致？→ 聚合字段逐项对齐（gmv/refund/new_users/cost/roi 的除零处理），用 full outer join 逐日对账，diff=0 才算过。
- 追问 2：pandas 会不会内存爆？→ 90 天、8 万订单的量级不会；再大就分片或只保留 Spark。
- 追问 3：怎么证明不是「假 Spark」？→ `--engine spark` 与 `--engine pandas` 分别落报告，`reports/reconcile_spark_*.md` 可查；Spark 失败时 `run_daily` 显式降级并记录真实引擎。
- 答不上来时：我没有集群调优经验，只做到本地 `local[2]` 跑通；生产环境的 executor 内存、shuffle 调参是我下阶段要补的。

### Q3. 为什么按日删写 + 唯一键 upsert，而不是每天全量重算整表？

- 30 秒版：按日删写只影响当天分区，重跑成本低；唯一键 upsert 处理维度变化；全量重算在 90 天全量时会把单日失败放大成整表重跑，且难以定位哪一层出错。
- 追问 1：删除当天数据时读到一半怎么办？→ `GET_LOCK` 命名锁串行化同一天任务，失败 rollback；并发第二个任务直接失败退出 3。
- 追问 2：唯一键怎么设计？→ 粒度键 + 分区列，例如 DWS 是 `(dt, channel_id)`，唯一键必须含 `dt`，否则分区表无法保证跨分区唯一。
- 追问 3：维度表也删写吗？→ 用户画像用 SCD2 关旧开新，商品/渠道按自然键 upsert，不按日删。
- 答不上来时：更复杂的增量合并（merge on change）我没做，当前是日批全量快照 + 按日覆盖。

## ② 最难的问题（真实案例）

### Q4. Spark 端到端重跑报 1062 Duplicate entry，怎么定位和修的？

- 现象：先跑 pandas 再跑 Spark 重算同一天，persist 阶段报 `1062 Duplicate entry`，撞 `stg_dws_daily_channel_spark` 主键。
- 定位：看 `etl_run_log` 定位到 persist 层；对比两张 staging 表，发现 pandas 写入时按 `engine` 过滤删除，只清了 `engine='pandas'` 的旧行，Spark 行残留；同一天再插就撞唯一键。
- 根因：跨引擎共用一张 staging 表，清理条件带了引擎维度，违背「本表按日期窗口整体覆盖」的 ADR。
- 修法：`rebuild_dws_pandas._write_stg` 的 DELETE 去掉 `engine` 过滤，按日期窗口整体清空；回归 `pytest -q` 48 passed，Spark 重跑 diff=0。
- 防回归：把「先 pandas 后 spark 同日重跑」列为 L2 固定场景（复盘建议 #5）。
- 追问 1：为什么不给唯一键加 engine？→ 那会把同一业务粒度拆成两份，DWS 下游要合并，违背 single source of truth。
- 追问 2：怎么确认不是 Spark 写入并发？→ 单任务串行执行且有命名锁，错误是唯一键冲突不是死锁。
- 追问 3：如果两个引擎同时跑？→ 不允许：`GET_LOCK` 按日期互斥，第二个任务退出 3。
- 答不上来时：更细的 Spark 执行计划我没逐 stage 分析，定位主要靠日志和表数据对比。

### Q5. DQ 规则两套实现口径不一致，怎么发现、怎么修、怎么防？

- 现象：3% 脏数据下 Python 复跑与 SQL 内联结果恰好一致，代码 Review 时逐条比对才发现 3 处口径不同。
- 定位：Review 对照 D-36「双实现结果不一致即缺陷」，逐字段比对：DQ03 负金额计数（全量含重复 vs 去重 rn=1）、DQ04 分母（ODS 总行数 vs DWD 行数）、`dq_alert` 触发范围（所有 warn vs 仅 P0/DQ05）。
- 根因：同一规则写在 Python 和 SQL 两处，没有单一事实源，脏数据类型重叠时必然分歧。
- 修法：统一为 SQL 去重集合与 ODS 分母口径，告警只写真实 P0 与 DQ05；修复后 5 天样本逐字段比对一致，`pytest -q` 48 passed。
- 防回归：建议加「Python 规则结果 == SQL 规则结果」对照用例（复盘建议 #4）。
- 追问 1：为什么当初写两套？→ 设计要 Python 独立复跑做第二意见，但没定「谁是权威口径」。
- 追问 2：怎么保证 3% 数据能覆盖分歧？→ 造数要构造类型重叠的脏单，不能只靠默认 3% 非重叠。
- 追问 3：现在谁是权威？→ SQL 内联是生产口径，Python 复跑必须对齐它。
- 答不上来时：更彻底的方案是单一 DSL 生成两边 SQL，这是我下版本想做的（见 Q7）。

### Q6. 交付前安全扫描发现 MySQL 端口映射到 0.0.0.0，怎么处理的？

- 现象：8.5 安全扫描发现 `docker-compose.yml` 写的是 `53306:3306`，局域网可直连数据库。
- 定位：扫描清单逐项核对 compose 端口；`Get-NetTCPConnection` 确认监听在 `::`/`::1` 全接口。
- 根因：本地开发图省事，端口映射没限定回环地址；初始化 SQL 还给账号授了 `@'%'`。
- 修法：改为 `127.0.0.1:53306:3306`，重建容器后复查监听只剩 `127.0.0.1`；数据卷保留，21 表/96,274 行完好。账号 `@'%'` 收紧列入 deferred（Q-008）。
- 防回归：建议把「compose 端口必须回环」纳入环境预检（复盘建议 #2）。
- 追问 1：为什么不当场改账号？→ 改账号要同步初始化 SQL 与所有连接配置，属于迭代线，先收口暴露面。
- 追问 2：怎么确认容器重建没丢数据？→ 挂载命名卷，重建后查 `dwd_order_detail` 16,748 行与备份一致。
- 追问 3：还有哪些暴露面？→ secrets 扫描 0 命中；SAST 1 处常量表名误报已豁免；输入层 11/11 通过。
- 答不上来时：生产环境还要做网络 ACL、TLS、审计日志，本项目只做到本机回环。

## ③ 再做一次

### Q7. 再做一次，DQ 双实现会怎么改？

- 30 秒版：把 DQ 规则收敛成一份配置/DSL，SQL 侧由模板生成，Python 侧调用同一份规则定义，只保留一个口径源；Python 复跑只做执行器，不再各写一套判断。
- 追问 1：DSL 长什么样？→ 规则 ID、级别、目标表、过滤条件、统计表达式、阈值；生成 SQL 片段，Python 用同一条件拼查询。
- 追问 2：怎么迁移？→ 先让 Python 调用 SQL 视图/函数取数，保证结果一致，再逐步替换内联 SQL。
- 追问 3：代价是什么？→ 多一层生成逻辑，调试要看生成后的 SQL；换来的是口径不再漂移。
- 答不上来时：我没实际做过规则引擎，只做到「两套实现 + 对照测试」，DSL 是下版本计划。

### Q8. 再做一次，调度层会怎么改？

- 30 秒版：现在靠脚本 + `backfill.py --retry-failed` 手工补跑；再做会引入带依赖 DAG、自动重试、失败告警的轻量调度（Airflow 或 cron + 任务表），把「哪层失败从哪层续跑」变成调度器状态机。
- 追问 1：为什么现在不做？→ 单人、单机、日批，Airflow 的元数据库和 Web 服务占内存，收益低于成本；先把链路正确性做扎实。
- 追问 2：轻量方案怎么做？→ `etl_run_log` 已有分层状态，用任务表 + cron 轮询失败层即可，不必上整套平台。
- 追问 3：怎么保证不重复跑？→ 调度器加幂等键（日期 + 层），复用现有 `GET_LOCK` 和按日删写。
- 答不上来时：Airflow 我只搭过 demo，没有生产运维经验。

## ④ 细节深挖

### Q9. 幂等具体怎么保证？

- 30 秒版：四层：`GET_LOCK` 按日期互斥；每层按 `dt` 删写；聚合表唯一键 upsert；成功层带行数预检，已成功则跳过。
- 追问 1：锁拿不到怎么办？→ 第二个任务失败退出 3，`etl_run_log` 记 `E_LOCK_CONCURRENT`。
- 追问 2：中途失败怎么续跑？→ `etl_run_log` 记录每层状态，从失败层开始，已成功层跳过。
- 追问 3：预检会不会误判？→ 预检按「层 + 日期 + 行数 > 0」，空结果日会跳过，这是预期而非故障。
- 答不上来时：`GET_LOCK` 返回 NULL 的分支还没覆盖（Q-002），计划改判 `v_lock <> 1`。

### Q10. 对账怎么做的？

- 30 秒版：Spark 重算写 staging，与存储过程结果按 `dt + channel` full outer join，金额容差 0.01，缺行或计数不等也算差异；有差异退出 4，报告落 `reports/`。
- 追问 1：为什么用 full outer join？→ 能同时发现「多行」和「缺行」，inner join 会漏掉缺行。
- 追问 2：除零怎么处理？→ ROI 分母为 0 时统一返回 NULL/0，两引擎同一套规则。
- 追问 3：怎么证明对账不是自证？→ 两边独立实现（存储过程 vs pandas/Spark），同一份源数据，逐日对比。
- 答不上来时：更细的金额精度（decimal 位数）我是按表定义对齐，没做逐笔流水级对账。

### Q11. 分区表和唯一键为什么必须带分区列？

- 30 秒版：MySQL 分区表的唯一键必须包含分区列，否则无法保证跨分区唯一；DWD/DWS 按月 `RANGE COLUMNS(dt)` 分区，唯一键是「业务粒度 + dt」。
- 追问 1：没有 pmax 会怎样？→ 超出范围的数据插入失败；保留 `pmax` 兜底，避免月初写入报错。
- 追问 2：分区裁剪怎么验证？→ `EXPLAIN` 看 `partitions` 只命中目标月，Q1 优化后走索引范围扫描。
- 追问 3：按日删写会不会锁全表？→ 只删当天分区范围，配合索引；日批单任务，不追求高并发。
- 答不上来时：更细的分区维护（自动加月分区）我没做，目前靠 `pmax`。

### Q12. 慢查询优化为什么没达到 3 倍？

- 30 秒版：三条查询都改了执行计划：Q1 加日期下推走索引范围扫描，Q2 加 SCD2 `is_current=1` 过滤，Q3 用 LAG 窗口替代自连接。但基线只有 19 天、1.7 万行，优化前后都在毫秒到百毫秒，数据量不足以放大收益，实测 0.79×/1.05×/0.79×，没达标就如实写。
- 追问 1：怎么确认优化生效？→ `EXPLAIN ANALYZE` 连续 5 次取中位数，看 rows 从 85,099 降到 42,549、索引名和窗口函数都在计划里。
- 追问 2：怎么才能达标？→ 跑完 90 天全量（8 万订单）再复测；Q3 的 ADS 表才 63 行，窗口函数优势要数据量起来才明显。
- 追问 3：为什么不改写成别的？→ 当前瓶颈是数据量不是 SQL，继续改是过度优化；先如实记录，等数据量到位再测。
- 答不上来时：更深层的 MySQL 优化器参数、直方图统计我没调过，只做到索引与执行计划层面。
